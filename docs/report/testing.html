Serial Data Issues

Ran into a problem where my code was receiving bad data over serial from the micro:bit.

.csv lines were missing values, had extra commas, or too few commas. This in turn would break my modelling script as it returned an out-of-range error when fetching the values.

How I investigated and rectified these problems

I looked online for anyone with a similar issue: Forum post

I found a forum post explaining that having the Makecode website open while my Python code was running was causing garbled values to be sent.

Evidence showing how I fixed the problem

I fixed this problem by closing the Makecode website when my code was running. I also implemented a failsafe if bad values were sent. The addition to my code is shown here, highlighted in red

Embedded System Algorithm

Model Equation

The algorithm I used to evaluate fire risk is 

                
                risk =  (light/200) + 
                        (temp/100)+
                        (1-(soil/100)) + 
                        (1 - (air/100)) / 4
.

Each value in my equation is read from the sensors. Temperature is generally read between 0 and 100 in the forest, so I divide it by 100 to ensure it is no bigger than 1.


To show this algorithm working, I will sample a line of data from my log.csv file


           Timestamp, Light, Temperature, Soil Moisture, Air Humidity, Flame
           2026-03-18 09:35:56.238918,93,25,77,16,0

Inputting these values gives

  
                risk =  (93/200) + 
                        (25/100)+
                        (1-(77/100)) + 
                        (1 - (16/100)) / 4

                        Solving this equation gives 0.446 or a 44.6% risk of fire

Higher soil moisture and air humidity values mean less chance of fire, which is why it is (1-soil_moisture) and (1-air_humidity). All values are divided by the max value that can be detected and then further divided by 4. This ensures the output risk of fire is a decimal between 0 and 1. This number is then multiplied by 100 to get the percentage value. You may notice that light is divided by 200, this is because the sensor had a tendency to read numbers almost exclusively in the 90's reacting very little to tests such as shining a torch on it, increasing only by 1 or 2 points

Limitations

A limitation I overlooked in development was the possibility of negative temperature values. This could lead to a negative fire risk being returned, which would not break the code but logically does not make sense.
